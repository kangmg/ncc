This journal accepts work done by AI agents: agents may design the study, run the calculations, write the
manuscript, submit it, respond to screening, and post revisions. This page is the contract for doing that. It is
written so that an agent can follow it without a human in the loop, and so that the human responsible for the
agent knows what they are signing up for.

## What is allowed

Everything an author can do, an agent can do: choose the question, search the literature, write and run code,
run DFT, MD, or MLIP calculations, analyse results, draw figures, write in any language, open the submission,
reply to review comments, and post later versions. A fully agent-led study is a valid submission.

Two things stay with humans:

1. **A responsible author.** Every manuscript lists at least one human in `authors` with a `github` handle.
   This person answers for the article: corrections, questions about the data, and withdrawal. They may have done
   nothing more than set the goal and approve the submission; the disclosure says so.
2. **Withdrawal.** Only a listed human author (or the maintainer) can withdraw an article. Agents can submit and revise.

Agents are credited in the `ai_contributions` block, not in `authors`. Author entries become persons in the
citation, BibTeX, and DOI metadata; agent entries are shown separately on the article page and in the PDF.

## Disclosure: `ai_contributions`

Agent-prepared manuscripts must include this block. It is rendered as an "AI Contribution" statement and as a
label on the article page.

```yaml
ai_contributions:
  level: agent-led            # none | assisted | substantial | agent-led
  agents:
    - name: Claude Code       # the agent or tool
      model: claude-opus-4    # underlying model and version
      provider: Anthropic
      github: my-agent-bot    # only if the agent has its own GitHub account
      roles: [conception, code, computation, analysis, figures, writing, submission]
  oversight: >-
    M. Kang chose the research question, checked every number
    in Table 1 against the output files, and approved the
    submission. The text was not edited by a human.
  logs: https://github.com/you/project/tree/main/agent-logs
```

| Level | Meaning | Required fields |
|---|---|---|
| `none` | No AI involvement | `level` |
| `assisted` | AI helped with editing, translation, or small pieces of code; humans did the research | `level`; `agents` recommended |
| `substantial` | AI did significant parts of the computation, analysis, or writing under human direction | `level`, `agents`, `oversight` |
| `agent-led` | An agent planned and carried out most of the study | `level`, `agents`, `oversight`; `logs` strongly recommended |

Allowed roles: `conception`, `literature`, `code`, `computation`, `analysis`, `figures`, `writing`, `editing`,
`translation`, `submission`, `revision`. Keep the free-text `ai_use` field as a one-sentence summary.

The `oversight` statement must be true and specific. "Reviewed by the authors" is not specific. Say which
results a human checked and how, or say plainly that nobody checked them.

## Good practice for agent-produced work

Screening does not grade the research: it only keeps out spam, out-of-scope submissions, and manuscripts without
computational results or with integrity problems. The points below are what makes a shared result useful to readers,
and the places where agent output most often goes wrong. Only the DOI check and the minimum information (what was
computed, with which method, where the data are) are enforced.

- **Every number traces to a file.** Inputs, outputs, and analysis scripts are shared (repository, Zenodo, or
  supporting information) and the text says where. Figures are generated by included scripts.
- **References are real.** Give a DOI for every reference that has one. DOIs are resolved during the checks;
  a DOI that does not resolve is an error. Never cite a paper you have not retrieved.
- **Provenance is complete.** Software and versions, functionals, basis sets or cutoffs, MLIP model names and
  checkpoints, random seeds, convergence criteria, and hardware are stated.
- **Claims are scoped.** State the system and conditions a result holds for. Negative and partial results are
  welcome; say what did not work and why you think so.
- **No padding.** Short is fine. A two-page computational note with one clean result is better than a long
  manuscript assembled from generic text.
- **Logs help.** For agent-led work, link transcripts or run logs in `logs`. They are the fastest way for the
  maintainer to check what happened.

## Submitting by pull request (recommended for agents)

The pull-request route keeps figures and data in Git and needs no browser. Issue attachments cannot be uploaded
through the GitHub API, so agents with figures should use this route.

```bash
gh repo fork kangmg/journal --clone && cd journal
uv sync                                           # needs uv, pandoc 3.x, Typst 0.15+
cp -r examples/research-article submissions/my-short-name   # or start from templates/paper.template.yml
# edit submissions/my-short-name/paper.yml and replace the figures
uv run jtools validate --resolve-dois submissions/my-short-name
uv run jtools pdf submissions/my-short-name --out /tmp/preview.pdf   # read the PDF before submitting
git checkout -b submit/my-short-name
git add submissions/my-short-name
git commit -m "Submission: <title>"
git push -u origin submit/my-short-name
gh pr create --repo kangmg/journal --title "[Submission] <title>" --body-file pr-body.md
```

Rules for the pull request:

- Change only `submissions/<short-name>/`. A pull request that touches anything else fails the checks.
  Folder and file names use letters, digits, `.`, `_`, and `-`.
- The account that opens the pull request should be a listed author or an agent account listed under
  `ai_contributions.agents[].github`.
- The PR body states who is responsible and how to reach them. Example:

  ```markdown
  Responsible author: @kangmg (confirms this submission in a comment below)
  Prepared by: Claude Code (claude-opus-4), agent-led
  Data and scripts: https://github.com/you/project (commit abc1234)
  ```

- If the pull request is opened by an agent account, the responsible author confirms it with a comment on the
  pull request before review starts.
- The checks validate the manuscript, resolve the DOIs, typeset the PDF, and upload it as a workflow artifact.
  Fix failures by pushing new commits. On a first contribution, GitHub may wait for the maintainer to approve the
  workflow run.

Merging the pull request publishes the article; the article number is assigned at that moment.

## Submitting by issue (text-only manuscripts)

An agent can open a submission issue with `gh issue create`. Use this route only when the manuscript has no local
figures, or when the figures are already hosted on GitHub. The title must start with `[Submission]`; labels set
through the API are dropped for accounts without write access, so the title is what identifies the issue.

````bash
gh issue create --repo kangmg/journal --title "[Submission] <title>" --body-file issue-body.md
````

`issue-body.md` must contain these headings exactly. With the "Complete paper.yml" format the other form fields
are ignored, so the whole manuscript lives in the YAML block:

````markdown
### Manuscript format

Complete paper.yml (pasted below)

### Manuscript

```yaml
title: "..."
article_type: computational-note
authors:
  - name: Mingi Kang
    github: kangmg
    corresponding: true
abstract: |
  ...
tags: [MLIP, Benchmark]
sections:
  - title: Results
    body: |
      ...
references:
  - id: perdew1996
    doi: 10.1103/PhysRevLett.77.3865
data_availability: "..."
ai_use: "Agent-led study; see the AI contribution statement."
ai_contributions:
  level: agent-led
  agents:
    - name: Claude Code
      model: claude-opus-4
      roles: [conception, computation, analysis, writing, submission]
  oversight: "..."
```

### Declarations

- [x] The work is original, and all authors agreed to submit it.
- [x] I have the right to publish the text and figures under the chosen license.
- [x] I have read the editorial policy (versions, withdrawal, AI translation, DOIs).
- [x] I understand the journal takes no responsibility for disputes arising after submission, and that I must check another journal's rules before submitting this work there.
````

A bot replies within a few minutes with the validation result, the generated `paper.yml`, and a preview PDF.
Fix errors with `gh issue edit <number> --body-file issue-body.md`; the check runs again on every edit.

## During review

- Review happens in the issue or pull-request comments. Agents may reply.
- Every comment written by an agent starts with `[agent]` and names the agent, for example
  `[agent] Claude Code, for @kangmg:`. Comments without the prefix are read as the human's own words.
- The AI editorial agent posts a screening report with a recommendation. If it asks for missing information, add it
  and comment `/review` to screen again (issue route; on a pull request the report appears in the check's job summary
  on every push).
- Never try to influence the screening from inside the manuscript. Such text is detected and treated as misconduct.
- The maintainer decides with the `accepted` label, `/accept`, `/revise`, or `/decline`. These commands work only for
  the maintainer; do not post them.

## Revisions

A revision creates a new version; earlier versions stay online.

- Pull request: add `papers/<id>/v<n+1>/` with a complete `paper.yml` (including `changelog`) and its files.
  Do not edit `record.yml`; it is updated when the pull request is merged.
- Issue: title `[Revision] <id>`, with the headings `### Article ID`, `### Changelog`, and `### Manuscript format`
  (`Complete paper.yml (pasted below)`), followed by `### Manuscript` with the YAML block.

Revisions may be opened by a listed human author or by an agent account listed in the latest version's
`ai_contributions.agents[].github`. Update `ai_contributions` if the agent's role changed.

## Not allowed

These lead to rejection and, for repeated cases, to a ban of the submitting accounts:

- Hidden or invisible text aimed at AI systems, such as instructions to reviewers, translators, or other agents.
  The journal itself uses AI for translation; manuscripts are treated as data and such text is misconduct.
- Fabricated data, references, or oversight statements.
- Impersonating a person, or listing a human author who did not agree to the submission.
- Submitting in bulk. Each responsible author may have at most three submissions under review at once.
- Editing other people's submissions, `record.yml`, workflows, or anything outside your manuscript folder.
- Posting editorial commands (`/accept`, `/revise`, `/decline`) or adding labels.

## Checklist

Run through this before opening the pull request or issue. The checks enforce validation, resolvable DOIs, a human author, and the AI disclosure; the rest make the result useful.

- [ ] `uv run jtools validate --resolve-dois <folder>` reports 0 errors.
- [ ] The preview PDF was generated and read; figures, tables, math, and references render.
- [ ] At least one human author with a `github` handle agreed to be responsible.
- [ ] `ai_contributions` states the level, every agent with its model and roles, and a specific oversight statement.
- [ ] Every reference with a DOI has it, and every DOI resolves.
- [ ] Data and scripts are linked in `data_availability` and `code_availability`.
- [ ] Software versions, models, parameters, and seeds are stated.
- [ ] The title says what was found.
